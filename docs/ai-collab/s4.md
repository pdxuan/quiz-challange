- Task: `QuizHub` (`JoinQuiz`, `WatchQuiz`, `SubmitAnswer`, disconnects), `SignalRSessionEvents`

## Design choices made while building

- The hub is untyped (`SendAsync` with event names): `QuestionClosed` and `QuizFinished` have
  one payload for each player and another for the organizer (Contract).
- `Publish` runs on the actor and does no I/O: it builds every payload from the committed session
  and queues the sends; one background loop sends them in order.
- `AnswersCount`: the first count is sent at once, later ones within 200 ms are merged into one
  (latest value) sent when the interval ends (a `TimeProvider` timer, so tests drive it); a
  count still pending when the question closes is dropped.
- `JoinQuiz` adds the connection to the session group *before* asking the actor, so no event
  between the commit and the reply is missed; on failure it is removed again. A second tab
  replaces the first: the old connection leaves the group, and personal pushes go to the
  connection stored on the player row.
- `SubmitAnswer` stamps `receivedAt` before the call is queued. Errors are a `HubException`
  whose message is only the code; an unexpected failure is `ServerError`.
- Groups: `quiz:{id}` (everyone) and `quiz:{id}:organizer` (full board).
- Outside the S4 Files list (TRUNK): `Domain/Session.CurrentAnswerCounts()` (public view of an
  existing private count) and the approved test package `Microsoft.AspNetCore.SignalR.Client`.

## What the AI got wrong or had to correct

- Primary-constructor parameters are not visible from a nested class (CS1061); kept them as
  fields.
- Two tests were wrong, not the server: (1) a "late" joiner joined at the very instant the
  question started (the fake clock had not moved), which the domain rightly treats as on time;
  the test now moves the clock 1 s first. (2) The 20-player test fired answers without awaiting
  while advancing the clock, so the server stamped later times than expected; all 20 now answer
  at once at a fixed time, which also matches "concurrently" in AC19.
- Reviewer agent (Must): AC25's "leaderboard stays readable after a restart" had no test.
  Added one (finish a quiz over the hub, start a new server on the same SQLite file, read the
  board). The behaviour already existed (S3 reads straight from SQLite), so the test passed
  at once; it was shown red by hiding finished sessions in the leaderboard query, then restored.
- Reviewer agent (Should, picked by the interviewer): (1) `WatchQuiz` joined its groups after
  the snapshot, so an event in between was lost -> groups first, as in `JoinQuiz`; (2) one
  outbox for all sessions let a slow client delay every session's pushes -> one ordered outbox
  per quiz that drains only while it has work (no deterministic test; review); (3) no hub test
  for `ServerError` -> added (corrupted row, code only, next call works); (4) AC13 lacked
  "rejoin after a disconnect" -> added (points kept, back online, one row); (5) a failed
  `JoinQuiz` on the organizer's watching connection removed it from the session group -> the
  hub tracks the connection's groups and removes only what a failed call added (test red
  first). Tests (3), (4) and the `WatchQuiz` group test passed at once (the behaviour existed)
  and were shown red by mutations below.
- A draft of the 20-player test computed the expected ranks from the database it was checking;
  rewritten to compute points and ranks from the inputs alone.

## How it was verified

- Tests seen red first: the test project did not compile without `SignalRSessionEvents`; the
  behaviours were then shown red by the mutations below.
- Then green: 186 server tests (24 new hub tests) covering AC4 (hub), AC8 push, AC10-AC13,
  AC15-AC21, AC23-AC27, AC30 and the hub error codes `QuizNotFound`, `QuizFinished`,
  `SessionFull`, `IsOrganizer`, `NotOrganizer`, `NotJoined`, `NotStarted`, `NotCurrentQuestion`,
  `NotEligible`, `QuestionClosed`, `AlreadyAnswered`, `Invalid` (from `SubmitAnswer`) and
  `ServerError`. Not tested at hub level: `Invalid` from `JoinQuiz` (the name comes from the
  auth cookie and the connection id is never empty, so the hub cannot produce it).
